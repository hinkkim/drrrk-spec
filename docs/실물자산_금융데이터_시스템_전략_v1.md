# 드르륵 실물자산 금융데이터 시스템 전략 v1

> 작성 배경: Shorooq Partners 미팅 이후 과제 — "드르륵 비즈니스 모델을 중동에 어떤 방식·방향으로 이식할 것인가"에 대해, DMCC(Tradeflow) 리서치 인사이트를 기반으로 **국내에서 지금 만들어야 하는 임팩트**와 **자체 구축 가능한 데이터 시스템**을 정의한다.
>
> 전제 조건 (현재 상태):
> - 자본금 소진 — 신규 리소스 투입 불가
> - 거래 등록 1~3건/일, 바이어 접속률 낮음, 반복입찰률 낮음
> - 드르륵에셋: Gemini API로 사진 기반 자산 식별 + 시장가격 추정 중이나 **정확도 낮음**

---

## 1. 프레임 정의 — DMCC 인사이트를 드르륵에 적용하면

DMCC Tradeflow의 본질은 마켓플레이스가 아니라 **"실물자산의 소유권·담보권 중앙 레지스트리"**다. UAE 창고에 보관된 상품에 대해 전자 권리증서(Tradeflow Warrant)를 발행하고, 은행이 그 증서를 담보로 금융을 실행한다. 즉 **실물 재고를 '금융 가능한 자산'으로 바꿔주는 데이터 인프라**가 핵심이고, 거래 자체는 그 위에서 일어나는 결과물이다.

이 프레임으로 드르륵을 다시 정의하면:

| | DMCC Tradeflow | 드르륵 (목표 상태) |
|---|---|---|
| 대상 자산 | 창고 보관 상품 (귀금속, 커피, 차 등) | 동산 실물자산 (명품 시계·가방·주얼리 등) |
| 핵심 산출물 | 소유권·담보권 증서 (Warrant) | **자산별 가격·유동성·회수율 데이터** |
| 금융 실행 주체 | 은행·파이낸스 하우스 | 전당포 바이어 (대부업 면허) |
| 플랫폼의 역할 | 신뢰 가능한 등기부 | 신뢰 가능한 **가격 발견 + 처분 실적 원장** |

**결론: 드르륵이 중동에 이식할 것은 "한국식 전당포 역경매 마켓플레이스"가 아니라, "동산 담보의 안전 금융 한도를 산출하는 데이터 엔진"이다.** Shorooq는 MENA 최초의 벤처 대출(venture debt) 펀드를 운영하는 자산 기반 금융에 깊은 하우스다 — 그들이 사고 싶은 것은 GMV가 아니라 "이 자산은 얼마까지 안전하게 금융할 수 있다"를 데이터로 증명하는 능력이다.

따라서 국내에서 지금 만들어야 하는 임팩트는 **거래량 성장이 아니라 "데이터 완결 거래"의 축적**이다.

## 2. 목표 파이프라인과 현재 시스템의 매핑

목표 파이프라인:

```
실물자산 등록
→ 자산 식별·정규화
→ 시장가격 추정
→ 실제 다수 바이어 견적 수집
→ 실제 거래가격 확보
→ 예상가격과 실제 처분가격 비교
→ 자산별 유동성·가격변동성 데이터 축적
→ "이 자산은 얼마까지 안전하게 금융할 수 있다"는 기준 생성
```

**핵심 판단: 이 파이프라인의 8단계 중 새로 "만들어야" 하는 시스템은 거의 없다.** 기능명세서 v3의 기존 플로우가 이미 각 단계의 이벤트를 생성하고 있다:

| 파이프라인 단계 | 이미 존재하는 소스 (명세서 근거) |
|---|---|
| 실물자산 등록 | 유저 담보물 등록 (§13.1, 사진 최대 10장 + 브랜드·모델·상태등급·구매연도) |
| 자산 식별·정규화 | Gemini 식별 (드르륵에셋) — **역할 재정의 필요, §4 참조** |
| 시장가격 추정 | 감정가 3-tier 구조 ② 견적 공고 기준 감정가 (§2.5) |
| 다수 바이어 견적 | 48시간 역경매 견적 (금리·대출금·기간·상환방식) |
| 실제 거래가격 | 낙찰 → 전자계약의 최종 대출 실행 조건 (§6단계) |
| 예상 vs 실제 처분가 | 유질물 처분 (§19.6) + 잔여금 반환 정산 (§19.7) — **처분가 기록 필드만 추가하면 됨** |
| 유동성·변동성 축적 | 감정가 3-tier의 ① 자산수첩 실시간 시세 — **이벤트 원장으로 통합 필요** |
| 안전 금융 한도 | LTV 50~70% 가이드 (§현재는 고정값) → **데이터 기반 카테고리별 커브로 대체** |

즉 문제는 "시스템을 새로 만들 리소스가 없다"가 아니라, **이미 발생하는 이벤트들이 하나의 정규화된 원장(ledger)에 쌓이지 않고 흩어져 있다**는 것이다. 필요한 것은 개발 리소스가 아니라 **스키마 설계 + 기록 규율**이다.

## 3. 자체 구축 가능한가 — 결론: 가능하다. 단, 설계를 바꿔야 한다

### 3.1 만들 것: 테이블 3개 + 주간 배치 1개

기술적으로 필요한 전부는 아래 수준이다 (Supabase 무료~저가 티어로 충분, 추가 인프라 비용 0원):

**① `asset_master` — 카노니컬 자산 사전**

```
canonical_asset_id | category | brand | model | reference_no | 별칭(검색용)
예: WATCH-ROLEX-SUBMARINER-126610LN
```

- 모든 가격 이벤트가 이 ID에 귀속된다. 데이터가 자산 단위로 모이게 하는 뼈대.
- 초기엔 국내 전당포 거래 상위 ~200개 모델만 수기로 구축해도 충분 (롤렉스·샤넬·에르메스·루이비통 상위 모델이 거래의 대부분).

**② `asset_instance` — 개별 실물**

```
instance_id | canonical_asset_id | 상태등급(S/A/B/C) | 구매연도 | 구성품 | 사진
```

**③ `valuation_event` — 가격 이벤트 원장 (시스템의 심장)**

```
event_id | instance_id (또는 canonical_asset_id) | event_type | value | ts | source | meta
```

`event_type` 열거값:

| event_type | 의미 | 발생 시점 |
|---|---|---|
| `ai_estimate` | AI 추정가 (신뢰구간 포함) | 등록 시 |
| `buyer_quote` | 바이어 견적 (대출금·금리·기간) | 48h 입찰 |
| `contract_price` | 낙찰·계약 확정 대출 조건 | 전자계약 |
| `extension_reappraisal` | 연장 심사 재평가 감정가 | 연장 신청 |
| `liquidation_price` | 유질물 실제 처분가 | 처분 완료 |
| `external_comp` | 외부 실현가 (sold 데이터) | 수시 수집 |

**④ 주간 배치 (스크립트 1개)** — 원장에서 파생 지표 산출:

- **추정 오차**: MAPE(ai_estimate vs contract_price/liquidation_price) — 카테고리·브랜드별
- **견적 스프레드**: 같은 매물에 대한 buyer_quote 최대/최소 격차 → **유동성·합의도 지표**
- **회수율**: liquidation_price ÷ 대출잔액 — 유질 시 실제 회수 성능
- **처분 소요일수**: 유질 개시 → 처분 완료
- **안전 LTV 커브**: 카테고리별 "실현가 하위 10% 시나리오에서도 회수율 100%가 되는 대출 비율" = **"이 자산은 X%까지 안전하게 금융 가능"의 정량적 정의**

이것이 파이프라인 마지막 단계의 실체다. 복잡한 ML이 아니라 **분위수 통계**로 시작한다.

### 3.2 정직한 제약: 하루 1~3건으로는 자체 거래만으로 부족하다

연 400~1,000건 등록으로는 카테고리×모델×상태등급별 통계 유의성 확보에 수년이 걸린다. 그래서 **거래량을 늘리는 전략(자본 필요)이 아니라, 건당 데이터 수율을 극대화하고 외부 데이터로 밀도를 보강하는 전략(자본 불필요)**을 쓴다:

**전략 A — 견적 자체가 데이터다 (거래 성사 불필요)**
등록 1건에 바이어 견적이 3~5개 붙으면, 거래가 성사되지 않아도 **대부업 면허를 가진 전문가의 가격 평가 라벨 3~5개**를 얻는 것이다. 등록 1건 = 가격 데이터 포인트 4~6개(AI추정 1 + 견적 3~5). 하루 2건이면 연간 3,000~4,000개 가격 이벤트. 유찰 건도 전부 원장에 기록하는 것이 규율의 핵심.

**전략 B — 파트너 전당포의 과거 장부 백필 (최대 레버리지)**
전당포는 수년치 [감정가 → 대출금 → 상환/유질 → 처분가] 기록을 이미 보유하고 있다. **파트너 바이어 3~5곳의 과거 2~3년 장부를 구조화해 백필하면, 자체 거래 3년치보다 빠르게 회수율·처분소요일 데이터를 확보한다.** 교환 조건은 현금이 아니라: Prime 등급 우대, 수수료 감면, 그리고 "당신 데이터가 반영된 AI 담보가치 조회 도구(P-11)" 우선 제공. 바이어 입장에서도 자기 감정 능력이 데이터로 증명되면 영업 자산이 된다.

**전략 C — 외부 실현가 캘리브레이션 레이어**
KREAM·번개장터·중고나라의 판매완료가, Chrono24 시세, 국내외 경매 낙찰가 등 **공개된 sold 데이터**를 `external_comp` 이벤트로 수집해 카테고리 시세 곡선의 기준선을 만든다. 자체 데이터는 이 기준선 대비 "담보 시장 할인율"을 측정하는 데 쓴다. (수집은 각 플랫폼 약관·저작권 범위 내에서 — 수기 주간 샘플링으로 시작해도 됨.)

세 전략 모두 개발자 1명이 파트타임으로 운영 가능한 수준이며, 자본 투입 없이 데이터 밀도를 10배 이상 올린다.

## 4. Gemini 부정확 문제 — 원인과 재설계

### 4.1 원인 진단

사진 → 가격을 LLM 한 번에 시키는 구조(one-shot)는 원리적으로 정확할 수 없다. LLM은 시세 테이블을 갖고 있지 않고, 학습 시점의 흐릿한 사전 지식으로 "그럴듯한 숫자"를 생성한다. 상태등급·구성품·연식에 따른 수십 % 가격 차이를 반영할 수 없다.

### 4.2 재설계: 식별과 가격 산정의 역할 분리

```
[사진] → Gemini: 식별·정규화만        → canonical_asset_id + 상태등급 후보
                (브랜드/모델/레퍼런스 추출)
[가격] → valuation_event 원장에서 조회  → ① 자체 견적·낙찰가 이력
                                        ② external_comp (sold 데이터)
                                        ③ 상태등급 조정계수
        → 출력: 점추정이 아닌 구간 (예: 850만~1,020만, 신뢰도 74%)
```

- **Gemini의 역할 축소**: "이 사진은 무엇인가"(식별)는 VLM이 잘하는 일이고, "얼마인가"(가격)는 못하는 일이다. 식별 결과를 `asset_master`에 매핑하는 데까지만 쓴다. 매핑 실패 시 유저에게 모델 선택지를 제시 (명세서 §13.1의 자동완성 입력과 결합).
- **가격은 항상 데이터에서**: 해당 canonical_asset_id의 최근 견적·낙찰·외부 comp의 분위수로 산출. 데이터 없는 모델은 "추정 불가 — 바이어 견적으로 확인하세요"로 정직하게 표시 (부정확한 숫자보다 신뢰에 유리하며, 역경매의 가치 제안과도 정합).
- **피드백 루프 자동화**: 바이어 견적이 도착하는 순간이 곧 ground truth 라벨링이다. `ai_estimate` vs `buyer_quote` 오차가 자동 계산되어 주간 배치에서 조정계수를 갱신한다. **드르륵의 역경매 구조 자체가 자기 교정 시스템이다 — 이것이 단순 시세조회 앱은 절대 가질 수 없는 구조적 해자다.**

### 4.3 명세서와의 정합

감정가 3-tier 구조(§2.5)는 그대로 유지된다. 바뀌는 것은 3종 감정가의 **산출 방법**이 "Gemini 추정" → "원장 기반 분위수 + 상태 조정"으로 교체되는 것뿐이다. ② 견적 공고 기준 감정가의 스냅샷 원칙, ③ 연장 재평가의 분리 원칙은 오히려 `valuation_event`의 `event_type` 구분으로 더 깔끔하게 구현된다.

## 5. 국내에서 증명할 임팩트 — KPI 재정의

거래량이 작은 상태에서 Shorooq에 보여줄 스토리는 "성장"이 아니라 **"데이터 엔진의 작동 증명"**이다. 다음 지표로 재정의한다:

| KPI | 정의 | 6개월 목표 (예시) |
|---|---|---|
| **데이터 완결 거래 수** | 등록→식별→추정→견적→계약(→처분)까지 전 체인이 원장에 기록된 건 | 누적 200건+ |
| **누적 가격 이벤트 수** | valuation_event 총 레코드 (백필·external 포함) | 10,000건+ |
| **추정 오차 개선 추이** | MAPE(추정 vs 낙찰가), 월별 | 30% → 15% |
| **견적 스프레드** | 카테고리별 견적 격차 (유동성 지표) | 상위 3개 카테고리 커브 확보 |
| **회수율·처분 소요일** | 유질 건 실측 (백필 포함) | 카테고리별 최초 공표 |
| **안전 LTV 커브** | 카테고리별 데이터 기반 한도 | 시계·가방 2개 카테고리 v1 |

이 지표 체계에서는 **하루 1~3건이라는 현재 거래량도 스토리를 훼손하지 않는다** — 건당 데이터 수율과 오차 수렴 속도가 증명 대상이기 때문이다. 오히려 "적은 거래로도 데이터 엔진이 수렴한다"는 것이 자본 효율성의 증거가 된다.

## 6. 중동 이식 방향 (요약)

1. **이식하는 것은 데이터 레이어다.** 한국의 대부업법 기반 역경매 마켓플레이스 그 자체는 UAE 규제 환경에 그대로 이식되지 않는다. 이식되는 것은 "동산 담보의 가격 발견 + 처분 실적 원장 + 안전 LTV 산출" 엔진이다.
2. **DMCC 생태계와의 접점**: DMCC Tradeflow가 창고 보관 상품의 권리 레지스트리라면, 드르륵은 **귀금속·시계·주얼리 등 고가 동산의 가치·유동성 레지스트리**로 포지셔닝 가능하다. 두바이는 금·시계 실물 거래의 글로벌 허브이고, 담보 기반 금융 수요가 구조적으로 크다.
3. **이슬람 금융 정합성**: 자산 기반(asset-backed) 구조는 이자 기반 무담보 대출보다 샤리아 호환 구조(무라바하·타와룩 등)로 설계하기 유리하다 — 실물자산 데이터 엔진은 그 전제 조건이다.
4. **Shorooq와의 정렬**: venture debt를 운영하는 하우스로서 Shorooq는 "담보 가치를 데이터로 언더라이팅하는 능력" 자체를 투자 논거로 이해한다. 국내 6개월의 KPI(§5)가 곧 중동 피치 덱의 트랙션 페이지다.
