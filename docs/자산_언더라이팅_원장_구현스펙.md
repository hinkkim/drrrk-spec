# 자산 언더라이팅 원장 (Asset Underwriting Ledger) 구현 스펙 v1

> 국내에서 먼저 증명할 시스템의 구체적 구현 스펙. 전략적 배경은 [`실물자산_금융데이터_시스템_전략.md`](./실물자산_금융데이터_시스템_전략.md) 참조.
>
> **설계 원칙**
> 1. 자본 0원: Supabase 무료~저가 티어 + 스크립트로 완결. 신규 인프라·인력 투입 없음.
> 2. 기존 플로우 무변경: 유저·바이어가 보는 화면은 그대로. 기존 이벤트 발생 지점에 기록 훅(insert)만 추가.
> 3. 원장 불변성: `valuation_event`는 append-only. 수정·삭제 없음 (오기입은 정정 이벤트로).
> 4. 정직한 출력: 가격은 항상 구간 + 신뢰도. 데이터 없으면 "추정 불가"로 표시.

## 1. 시스템 구성 (전체)

```
┌─ 기존 서비스 (변경 없음) ──────────────────────────────┐
│  드르륵 (역경매)          드르륵에셋 (자산 식별/시세)   │
│  등록→견적→계약→상환→유질  사진 업로드→Gemini 식별      │
└──────────┬────────────────────────┬────────────────────┘
           │ 기록 훅 (insert)        │ 식별 결과 매핑
           ▼                        ▼
┌─ 신규: 언더라이팅 원장 (Supabase) ─────────────────────┐
│  asset_master ── asset_instance ── valuation_event     │
└──────────┬─────────────────────────────────────────────┘
           │ 주간 배치 (스크립트 1개)
           ▼
┌─ 파생 산출물 ──────────────────────────────────────────┐
│  metric_snapshot (카테고리·모델별 주간 지표)            │
│  → Asset Score v0  → KPI 대시보드  → (Phase 3) PoC API │
└────────────────────────────────────────────────────────┘
```

## 2. 데이터 모델 (DDL)

### 2.1 `asset_master` — 카노니컬 자산 사전

모든 가격 이벤트가 귀속되는 표준 자산 ID. **초기 구축: 국내 전당 거래 상위 ~200개 모델 수기 입력** (롤렉스·샤넬·에르메스·루이비통 상위 모델이 거래 대부분을 차지).

```sql
create table asset_master (
  canonical_asset_id text primary key,        -- 예: WATCH-ROLEX-SUBMARINER-126610LN
  category           text not null,           -- WATCH / BAG / JEWELLERY / ETC
  brand              text not null,
  model              text not null,
  reference_no       text,                    -- 시계 레퍼런스, 가방 스타일코드 등
  aliases            text[] default '{}',     -- 검색·식별 매핑용 별칭
  created_at         timestamptz default now()
);
```

### 2.2 `asset_instance` — 개별 실물

```sql
create table asset_instance (
  instance_id        uuid primary key default gen_random_uuid(),
  canonical_asset_id text references asset_master,
  grade              text check (grade in ('S','A','B','C')),  -- 명세서 §13.1 상태등급
  purchase_year      int,
  accessories        jsonb,                   -- 보증서·박스 등 구성품
  source             text not null,           -- drrrk(거래) / backfill(백필) / asset_only(드르륵에셋 조회만)
  listing_id         text,                    -- 기존 거래 시스템의 매물 ID (join key)
  created_at         timestamptz default now()
);
```

### 2.3 `valuation_event` — 가격 이벤트 원장 (시스템의 심장, append-only)

```sql
create table valuation_event (
  event_id           uuid primary key default gen_random_uuid(),
  instance_id        uuid references asset_instance,
  canonical_asset_id text not null references asset_master,  -- 비정규화 (조회 성능)
  event_type         text not null check (event_type in (
    'ai_estimate',            -- AI 추정 (구간: meta에 low/high/confidence)
    'buyer_quote',            -- 바이어 견적 ★ Liquidation Value의 직접 관측치
    'contract_price',         -- 낙찰·전자계약 확정 대출 조건
    'extension_reappraisal',  -- 연장 심사 재평가 (명세서 §18)
    'liquidation_price',      -- 유질물 실제 처분가 ★ Recovery의 ground truth
    'external_comp',          -- 외부 sold 데이터 (KREAM/Chrono24 등)
    'backfill_appraisal',     -- 백필: 파트너 전당포 과거 감정가
    'backfill_loan',          -- 백필: 과거 대출 실행액
    'backfill_liquidation',   -- 백필: 과거 처분가
    'correction'              -- 오기입 정정 (meta.corrects = 원본 event_id)
  )),
  value_krw          bigint not null,
  observed_at        timestamptz not null,    -- 이벤트 발생 시각 (백필은 과거 일자)
  source             text not null,           -- buyer:{id} / gemini / kream / backfill:{partner} ...
  meta               jsonb default '{}',      -- 금리·기간·상환방식(quote/contract),
                                              -- 처분채널·소요일·비용(liquidation),
                                              -- low/high/confidence(ai_estimate) 등
  created_at         timestamptz default now()
);
create index on valuation_event (canonical_asset_id, event_type, observed_at);
```

### 2.4 `metric_snapshot` — 주간 파생 지표 (배치 산출)

```sql
create table metric_snapshot (
  snapshot_week      date not null,           -- 주 시작일
  canonical_asset_id text,                    -- null이면 category 레벨 집계
  category           text not null,
  market_value_p50   bigint,                  -- 외부 comp + 낙찰가 중위값
  liq_value_p50      bigint,                  -- buyer_quote 중위값
  liq_value_p25      bigint,                  -- 보수적 Liquidation Value
  bid_depth_avg      numeric,                 -- 매물당 평균 견적 수
  bid_spread_pct     numeric,                 -- (최고-최저)/중위 견적 — 유동성·합의도
  volatility_90d_pct numeric,                 -- 90일 가격 변동성
  mape_estimate_pct  numeric,                 -- AI 추정 vs 낙찰가 오차
  recovery_rate_pct  numeric,                 -- 처분가/대출잔액 (백필 포함)
  days_to_liquidate  numeric,                 -- 유질 개시→처분 소요일
  recommended_ltv    numeric,                 -- §4 산식
  sample_size        int not null,
  primary key (snapshot_week, category, coalesce(canonical_asset_id,''))
);
```

## 3. 이벤트 캡처 지점 (기존 플로우 → 원장 훅)

| # | 기존 플로우 시점 (명세서 근거) | 기록할 이벤트 | 구현 |
|---|---|---|---|
| 1 | 담보물 등록 완료 (§13.1) | `asset_instance` 생성 + `ai_estimate` | 등록 API에 insert 2건 추가 |
| 2 | Gemini 식별 (드르륵에셋) | `canonical_asset_id` 매핑 | Gemini 출력을 brand/model/ref JSON으로 받아 `asset_master.aliases` 매칭. 매칭 실패 → 유저에게 후보 선택 UI (§13.1 자동완성 재활용) |
| 3 | 바이어 견적 제출 (48h 역경매) | `buyer_quote` (금리·기간·상환방식 meta 포함) | 견적 제출 API에 insert. **유찰·미낙찰 견적도 전부 기록** |
| 4 | 전자계약 확정 (§6단계) | `contract_price` | 계약 확정 시 insert |
| 5 | 연장 심사 (§18) | `extension_reappraisal` | 연장 신청 시 insert |
| 6 | 유질물 처분 완료 (§19.6~19.7) | `liquidation_price` (처분채널·소요일·비용 meta) | **처분가·처분일 입력 필드 신설 필요** — 현재 명세에 처분 결과 기록이 없음. 바이어 처분 완료 신고 화면에 3개 필드 추가 (유일한 화면 변경) |
| 7 | 외부 sold 수집 (주간 수기) | `external_comp` | 상위 50개 모델 × 주 1회, 스프레드시트 → CSV 업로드 스크립트. 주 2~3시간 |
| 8 | 파트너 전당포 백필 | `backfill_*` 3종 | 엑셀 템플릿 배포 → 비식별화 → 일괄 import 스크립트 |

> **규율이 기술보다 중요하다**: #3의 "유찰 건 포함 전부 기록"과 #6의 "처분 결과 필수 입력"이 지켜지지 않으면 원장은 생존 편향(성사 건만 남는)으로 오염된다. 어드민 주간 체크리스트에 미기록 건 확인 항목을 넣는다.

## 4. Asset Score v0 산출 (주간 배치)

ML이 아니라 **분위수 통계**로 시작한다. canonical_asset_id별(표본 부족 시 카테고리로 폴백):

```
Market Value        = P50( external_comp ∪ contract_price, 최근 180일 )
Liquidation Value   = P25( buyer_quote, 최근 180일 )          ← 보수적 도매 호가
Net Recovery Value  = Liquidation Value × (1 − 처분비용률)     ← liquidation meta 실측치
Bid Depth           = 평균 견적 수 / 매물
Bid Spread          = (P90 − P10) / P50 of buyer_quote        ← 낮을수록 유동성·합의도 高
Volatility (90d)    = std( 주간 P50 변화율 )
Wholesale Discount  = 1 − Liquidation Value / Market Value    ← 드르륵만 관측 가능한 값
Recommended LTV     = P10(buyer_quote) × (1 − 처분비용률) / Market Value
                      ── "최악 분위 호가로 처분해도 원금 회수되는 대출 비율"
```

- 상태등급 조정: grade별 표본이 충분해지기 전까지는 S/A/B/C 조정계수를 백필 데이터에서 1회 추정해 곱한다.
- `mape_estimate_pct`가 매주 갱신되며 `ai_estimate` 표시 구간의 폭을 자동 보정한다 (오차가 크면 구간을 넓게 = 정직한 표시).
- 표본 기준: sample_size < 5 → Asset Score 미발행, "데이터 수집 중" 표시.

### PoC API 응답 형태 (Phase 3 목표물)

```json
{
  "canonical_asset_id": "WATCH-ROLEX-SUBMARINER-126610LN",
  "grade": "A",
  "as_of": "2026-08-10",
  "market_value_krw":       15200000,
  "liquidation_value_krw":  12400000,
  "net_recovery_value_krw": 11800000,
  "expected_days_to_liquidate": 21,
  "bid_depth": 5,
  "bid_spread_pct": 8.1,
  "volatility_90d_pct": 6.2,
  "recommended_ltv_pct": 55,
  "sample_size": 34,
  "confidence": "medium"
}
```

주의: 이 API는 "이 고객에게 얼마 빌려줘도 된다"를 절대 말하지 않는다. **자산 데이터까지만** — 승인·LTV 최종 결정은 금융기관 몫 (규제 정합 + UAE 구조 예행연습).

## 5. 구축 일정 (6주, 자본 0원)

| 주차 | 작업 | 리소스 |
|---|---|---|
| 1주 | `asset_master` 상위 200개 모델 수기 구축, DDL 4개 테이블 생성 | 수기 + Supabase 무료 티어 |
| 2주 | 캡처 지점 #1~#5 기록 훅 추가 (기존 API에 insert) | 개발 소규모 |
| 3주 | Gemini 역할 축소 리팩터: 식별 JSON → canonical 매핑 → 원장 기반 구간 표시 | 드르륵에셋 수정 |
| 4주 | 캡처 지점 #6 처분 결과 입력 필드 + #7 외부 comp 업로드 스크립트 | 개발 소규모 + 주간 수기 운영 시작 |
| 5주 | 백필 템플릿 확정, 파트너 전당포 1호 데이터 import | 영업(창업자) + 스크립트 |
| 6주 | 주간 배치(metric_snapshot) 가동, KPI 대시보드 v0 (Supabase 뷰 + 시트) | 스크립트 1개 |
| 7주~ | 데이터 축적 운영. Bid Depth ≥ 3 모델 80개 도달 시 Phase 3 (금융기관 PoC 제안) 개시 | — |

병행 (개발 외): 파트너 전당포 2~3호 백필 협의 / UAE 3대 검증 질문 발신 (전략 문서 §5).

## 6. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 바이어 견적이 적어 Bid Depth 부족 | 유찰 건 포함 전량 기록 + 백필로 보강. Bid Depth ≥ 3 모델부터 Score 발행 (전 모델 커버 불필요 — 상위 80개면 PoC 가능) |

| Gemini 식별 실패율 | 실패 시 유저 선택 UI 폴백. 실패율 자체를 주간 지표로 기록해 aliases 보강 |
| 처분 결과 미입력 (바이어 협조) | 입력 완료를 정산 프로세스 선행 조건으로 연결 (수수료 정산 §14.4와 결합) |
